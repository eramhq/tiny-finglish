# Working on this

## The three rules that matter

**1. The rule table has one source of truth.** `src/rules.ts` owns it;
`data/rules/graphemes.json` is generated by `scripts/export-rules.ts` and read
by Python. Never hand-edit the JSON — CI regenerates it and fails on drift. If
the two sides disagree about what `kh` means, the training corpus and the
browser runtime are silently solving different problems.

**2. The normalizer exists twice and must stay identical.** `src/normalize.ts`
and `training/tiny_finglish_training/normalize.py` are mirrors, pinned by
`data/fixtures/normalization.jsonl`, which both test suites run. Change one,
change the other, regenerate the fixture, and check the diff is what you meant.

**3. Never tune against `data/gold/`.** Not thresholds, not the rule table, not
the English word list, not hyperparameters. When a gold case fails, put a
*different* case exercising the same phenomenon into `data/fixtures/` and leave
the gold case alone.

## Adding a fixture

`data/fixtures/fixtures.jsonl`, one JSON object per line:

```json
{"id": "ambiguous-032", "category": "ambiguous", "input": "sabr",
 "expected": "صبر", "alternatives": [], "notes": "ص not س — Arabic loan."}
```

* `expected` must be **normalized**; `node scripts/run-fixtures.ts --id <id>`
  shows what the pipeline produced and every candidate it considered.
* `alternatives` are additionally-acceptable outputs, not second guesses. Use
  them where Persian genuinely permits more than one spelling.
* `expected: null` means "must not crash, no correct answer asserted" — for
  latency guards and degenerate input.
* `expectAction: "copy"` asserts the input passes through untouched.
* Write a `notes` line saying *why* the case is interesting. A fixture without a
  reason is a fixture nobody can maintain.

## Changing the model

The browser runtime is a hand-written reimplementation of the PyTorch forward
pass. Any change to `model.py` needs the matching change in `src/runtime.ts`,
and then:

```bash
cd training && .venv/bin/python -m tiny_finglish_training.parity \
    --checkpoint runs/<run>/best.pt \
    --weights ../data/fixtures/weights.json --out ../data/fixtures/parity.jsonl
cd .. && node scripts/parity.ts
```

Parity currently holds at **6.7e-6** worst-case logit delta against a 2e-3
tolerance. If a change pushes that toward the tolerance, something structural is
wrong — that is three orders of magnitude of headroom, and float noise does not
consume it.

Keep the ops parity-friendly: float32, RMSNorm not LayerNorm, ReLU not GELU, and
the recurrence in convex form. Every one of those is a deliberate choice to keep
the two implementations comparable.

## Running the budgets

```bash
node scripts/bench.ts    # fails the build over 16 ms / 100 ms
node scripts/size.ts     # reports; never fails
```

Latency is the hard gate and size is the soft one — deliberately. A keystroke
that misses a frame is paid on every character; a download one JPEG larger is
paid once.

## Things that look like bugs and are not

* **`salam` → `سلم`.** Both are attested Persian words. The lexicon has no
  frequency ranking, so nothing separates them. See `docs/open-items.md`.
* **Short-vowel quality varies in generated Finglish.** `ketab` and `kotab` are
  both reachable from کتاب. There is no redistributable Persian pronunciation
  dictionary; the generator samples. The syllable *structure* is engineered and
  is tested — see `test_syllable_structure`.
* **`SALAM` is not converted.** ALLCAPS matches the identifier pattern. A
  deliberate trade: preserving `API_KEY` matters more than converting shouting.
* **The rule baseline beats the model on top-3.** It generates more diverse
  candidates; the model's distribution is more peaked.
